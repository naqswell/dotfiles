# apk-send

Отправка сборки себе в «Избранное» Telegram одной командой.

## Как отправить

```
apk-send            # свежая сборка текущего worktree
apk-send mymts      # из конкретного репозитория под ~/mts
apk-send <путь>     # конкретный файл или каталог
```

Имя разбирается сперва как каталог рядом, и только потом как репозиторий. Если
одноимённый каталог есть, но сборок в нём нет, берётся репозиторий — так работает
`apk-send platsdk` из воркри platsdk, где `./platsdk` это модуль SDK, а не сборки.

Всё остальное скрипт делает сам: находит APK, читает из него версию и пакет
через `aapt2`, достаёт flavor/buildType из пути, вытаскивает ключ задачи из имени
ветки и собирает подпись. Занимает около 25 секунд на 400 МБ.

## Какая сборка выбирается

Не просто самая свежая. `assembleDebug` собирает все флейворы разом, и кто из них
лёг на диск последним — случайность, поэтому среди сборок **одного прогона**
предпочитается обычная: `debug` перед `release`, флейвор `default` (а также `main`,
`full`, `standard`) перед остальными. Сборки старше окна в 5 минут в это сравнение
не попадают — вчерашняя обычная не победит сегодняшнюю особую.

Если взята не самая свежая, скрипт скажет об этом строкой
`рядом более свежая … — беру обычную сборку`. Нужна именно она — передай путь явно.
Окно меняется через `APK_SEND_TIE_WINDOW` (секунды).

Ничего не добавляй к команде: ни `-c`, ни `--to`, ни своих подписей. Чат назначения
задать невозможно — так задумано, отправка всегда идёт строго в «Избранное».

## Имя файла

В «Избранном» лежат сборки со всех веток вперемешку, поэтому имя обязано нести
ветку. Скрипт достраивает его сам, приписка зависит от ветки:

| Ветка | Имя |
|---|---|
| `feature/PAY-690-fix`, `bugfix/…` | `…_6.74.0-PAY-690-fix-SNAPSHOT.apk` |
| `develop` | `…_6.74.0-develop.apk` |
| `release/*`, `master` | `…_6.74.0-release.apk` |

Если имя на диске уже такое — файл уходит как есть; демка platsdk собирает его
сразу правильным (`app/build.gradle.kts`). Ветку определить не удалось — имя не
трогается вовсе, чтобы не соврать. Файл в сборочном каталоге не переименовывается
ни в каком случае: под нужным именем уезжает жёсткая ссылка на него.

`versionName … не несёт ветку` в выводе значит, что имя файла поправлено, а
версия **внутри** APK осталась голой — в списке приложений на телефоне такую
сборку не отличить от собранной с `develop`. Лечится в сборке проекта, не здесь.

## Чего делать нельзя

**Никогда не вызывай `tdl` напрямую.** Он умеет отправлять в любой чат, а обёртка —
только в «Избранное» и только `*.apk`. Прямой вызов обходит оба предохранителя.
Если `apk-send` чего-то не умеет — скажи об этом пользователю, а не иди в обход.

Не отправляй ничего, кроме APK. Рядом в дереве лежат keystore, `local.properties`
и `gradle.properties` с корпоративными секретами.

## Если не сработало

| Что вывелось | Что делать |
|---|---|
| `не найден tdl` | `apk-send install` |
| `прокси … не отвечает` | xray лёг. Проверить: `lsof -nP -iTCP:10808 -sTCP:LISTEN`, поднять — `vpn` |
| `нет .apk` / `не нашёл ни одного .apk` | Сборки нет. Собрать её, а не искать APK где-то ещё |
| `это не APK` | Сборка ещё идёт либо файл не тот. Дождаться конца и повторить |
| `отправляю только *.apk` | Просили отправить не сборку. Так и должно быть — не обходи |
| `файл изменился прямо перед отправкой` | Идёт пересборка. Дождаться и повторить |
| `другая отправка уже идёт (pid N)` | Ждёт другой процесс. Если pid мёртв, скрипт снимет лок сам; вручную — `rmdir ~/.local/state/apk-send/lock` |
| `принимаю один аргумент` | Отправляй сборки по одной, отдельными вызовами |
| `не смог подготовить … к отправке` | Нет места под `~/.local/state/apk-send` либо каталог недоступен на запись |
| `нет такого файла, каталога или репозитория` | Опечатка в имени репозитория или пути |
| Просит авторизацию | Нужен `apk-send login` — это интерактивный вход по QR-коду, выполняет **пользователь**, сам не запускай |

`ВНИМАНИЕ: сборке больше суток` — не ошибка, но скажи об этом пользователю: скорее
всего он ждал свежую сборку, а отправилась вчерашняя.

## Отправка при git push

Хук `pre-push` ставится по репозиториям отдельно, из любого его worktree:

```
apk-send hook install     # apk-send hook status | uninstall
```

Хук отправляет сборку при двух условиях сразу: она **новее пушимого коммита**
и пуш **реально принят удалённой стороной**. Второе важно — `pre-push`
срабатывает до ответа сервера, поэтому отклонённый защищённой веткой пуш,
non-fast-forward и `git push --dry-run` иначе отправляли бы сборку под коммиты,
которых в remote нет. Подтверждение ждётся до 90 секунд через `git ls-remote`.

Push хук не задерживает и никогда не отменяет: ожидание и отправка уходят в фон,
лог дописывается в `~/.local/state/apk-send/last.log`. Если сборки нет, она
устарела или пуш не подтвердился — там будет причина.

Не предлагай ставить хук там, где уже есть свой `pre-push` — `apk-send` в этом
случае откажется затирать чужой файл, и это правильно.

## Проверить, не отправляя

```
APK_SEND_DRY=1 apk-send mymts
```

Показывает, какой файл выбран и какая будет подпись. Полезно, когда не уверен,
что автопоиск возьмёт нужную сборку.

## Что увидит получатель

```
Мой МТС (dev) 6.74.0-PAY-690-platsdk-update-SNAPSHOT
customizable/debug · ru.mts.mymts.debug
PAY-690 · bugfix/PAY-690-platsdk-update
12.08 15:40 · 73f8f694d1a
```

`versionCode` в подпись не идёт: у демки platsdk его нет вовсе, а там, где есть,
его никто не двигает — в подписи это шум, а не идентичность.

Ключ задачи — кликабельная ссылка на jira.mts.ru. Если в имени ветки ключа нет
(шаблон `[A-Z][A-Z0-9]+-[0-9]+`), в строке остаётся одно имя ветки.

Скрипт: `~/Projects/setup/remote-work-setup/bin/apk-send`, `apk-send help`.
